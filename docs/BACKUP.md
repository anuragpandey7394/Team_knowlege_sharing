# Local backup and recovery

Stop application writes and workers before a consistent validation run. Confirm DATABASE_URL identifies this project's dedicated local tka_dev database. Never reset or restore over an unknown database.

`npm run backup:verify` creates a PostgreSQL custom-format archive under ignored `.cache/backups/`, creates a uniquely named disposable `tka_restore_<uuid>_test` database, restores into it, compares all 19 application tables, exact published-version contents and memberships, checks immutable-version protection, then drops only that generated database. It preserves the source and archive. It fails if tooling, permissions, data or validation is missing. Host pg_dump/pg_restore must support the server version. To use matching tools inside the project's PostgreSQL container, set `TKA_POSTGRES_CONTAINER=tka-local-postgres-1`; CI supplies its own service-container ID. Do not point this option at an unrelated container.

Archives contain database contents and hashed credentials. Keep them out of Git, restrict local access and encrypt them before any off-machine storage. Current verification data is synthetic; do not treat this local runbook as approval to copy real employer information. There is no cloud backup configuration yet.

For manual recovery, first create a new disposable database with an explicit project-owned name. Restore using `pg_restore --exit-on-error --no-owner --no-privileges --dbname <new-database> <archive>` with credentials injected through PostgreSQL environment variables. Verify migrations, versions, membership isolation and application readiness before switching configuration. Preserve the previous database until validation is complete. Do not use `--clean`, database resets or destructive seed commands against an existing environment.

`npm run db:upgrade:verify` constructs the committed M04 schema in a generated schema within tka_test, inserts a synthetic published version and membership, applies the current migration chain, verifies preservation/backfill/immutability and drops only its generated schema. It requires full Git history containing the M04 commit; CI uses fetch-depth 0. Integration suites separately migrate new empty disposable schemas. On a failed migration, inspect Prisma migration status and the precise SQL failure before any repair. Prefer a reviewed forward fix; restore a backup into a new database if recovery is necessary. Never mark a failed/partial migration as applied without verifying its actual schema.
